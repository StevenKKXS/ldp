# Direction B Review

Date: 2026-05-18

## Verdict

Direction B is easier to implement than Direction A and is a reasonable first low-cost probe, but it has a higher risk of becoming ordinary behavior-cloning-style pretraining that does not improve downstream diffusion policy.

Given the user's preference to preserve the proven PTP structure, the first version should be PTP-compatible encoder pretraining, not a policy-side `condition = concat(original_PTP_condition, z_t)` modification.

## Clarification

The action sequence in Direction B is the pretraining target for an auxiliary decoder. It should not change PTP's downstream prediction horizon, rollout horizon, or action execution logic in the first pass.

## Current Code Observations

1. Existing PTP configs already have `obs_encoder_dir` and `obs_encoder_freeze` hooks. This makes encoder-pretraining integration feasible without changing policy architecture.

2. Current transformer policy computes condition as:

   ```text
   cond = obs_encoder(obs[:n_obs_steps]).reshape(B, To, Do)
   ```

   Policy-side concat would require changing condition dimensions or token count. That is not needed for the first pass.

3. With `past_action_pred=true`, the current transformer loss keeps the full action trajectory instead of slicing away past tokens. This makes Direction B conceptually close to PTP, but moves action-sequence supervision into a pretraining stage for the encoder.

4. `RobomimicReplayImageDataset.__getitem__` returns only the first `n_obs_steps` observations but returns an action sequence of length `horizon`, composed from past-aligned actions plus future actions. This is enough for both future-only and past+future auxiliary prediction targets.

5. Existing `obs_encoder_dir` loading expects a checkpoint payload whose `state_dicts['model']` contains keys starting with `obs_encoder.`. A standalone pretraining workspace must save a compatible checkpoint or provide a small conversion script.

## Strong Points

- Simpler than contrastive distribution matching.
- Directly aligns with the PTP intuition that past-token prediction helps.
- Produces clear pretraining diagnostics: action prediction loss, future-only vs past+future, frozen vs finetune.
- The auxiliary decoder can be discarded, so the downstream policy can remain exact PTP.

## Main Risks

1. **Low prediction loss may not transfer.**

   A decoder can learn average/BC-like action trends while the retained encoder is not better for diffusion policy.

2. **Decoder capacity can hide encoder weakness.**

   A strong transformer decoder may solve the pretraining task without forcing robust encoder features. First pass should use a small MLP decoder or low-capacity learned-query decoder.

3. **If the policy structure is unchanged, only `obs_encoder` transfers.**

   Current PTP temporal modeling is mainly in the transformer policy head. If pretraining uses a temporary temporal aggregator and then discards it, downstream only receives improved per-frame obs features. This is clean but may limit effect size.

4. **Historical action input changes the PTP information set.**

   If `a_{t-H:t-1}` is added to the encoder input in pretraining or policy, it is no longer exact PTP unless the baseline receives the same input. First-pass exact-PTP-compatible version should use the same observation inputs as PTP and defer historical action input to an ablation.

5. **Past+future prediction can become too easy.**

   If past actions are directly inferable from low-dimensional observations or are included as input, prediction loss may fall without improving future behavior representation.

## Updated First-Pass Recommendation

First pass should be:

```text
Exact PTP policy + predictive-pretrained obs_encoder
```

No policy-side condition concat.

No new retained history module.

Use the auxiliary action decoder only during pretraining and discard it for downstream policy.

## Minimal Workflow

1. Reproduce or identify the exact PTP baseline config/checkpoint for Square and ToolHang.
2. Create a predictive encoder pretraining workspace using the same robomimic obs encoder used by PTP.
3. Input: same observations as PTP first. Do not add historical actions in the first exact-PTP-compatible pass.
4. Target: normalized `batch['action']` full sequence for past+future, and optionally `batch['action'][:, n_obs_steps-1:]` for future-only.
5. Decoder: small MLP over flattened or pooled `B x To x Do` features.
6. Loss: Huber in normalized action space.
7. Save compatible encoder checkpoint.
8. Run load smoke with existing PTP config via `obs_encoder_dir`.
9. Compare:

   ```text
   B1. Exact PTP baseline
   O2. Exact PTP + past+future predictive encoder, frozen
   O3. Exact PTP + past+future predictive encoder, finetuned
   ```

10. Add future-only `O1` only after the past+future path is technically validated, unless resources allow parallel runs.

## B2 Interpretation

If the first pass does not add any retained policy architecture, then `B2` may not be distinct from `B1`. Do not invent a misleading `B2`.

Use `B2` only if:

- a new retained encoder/aggregator/fusion module is added to the policy, or
- a non-predictive pretraining baseline checkpoint is available and answers a specific control question.

## Recommended Observations Before Full Policy Runs

Before spending large GPU time, collect:

- train/val Huber loss for full action sequence,
- future-only action loss even when training past+future,
- per-timestep loss curve,
- per-action-dimension loss,
- frozen encoder nearest-neighbor action consistency,
- whether loss improves by predicting low-variance/gripper dimensions only,
- whether the encoder checkpoint loads into exact PTP without missing keys.

## Open Questions

1. What exact PTP baseline config and checkpoint should be considered canonical for Square and ToolHang?
2. Should first-pass target be full `batch['action']` or only the policy-executed future slice?
3. Should the decoder consume flattened `To` obs features, the last obs feature, or mean-pooled obs features?
4. What decoder capacity is acceptable before it becomes too strong?
5. Should future-only be run in the first matrix, or only after past+future validates the pipeline?

## Recommendation

Direction B should probably be the first implementation smoke after documentation review, because it is simpler than Direction A:

```text
dataset batch -> obs_encoder -> small MLP decoder -> Huber(action sequence)
```

But downstream validation should keep PTP unchanged. The result to trust is not pretraining loss; it is whether the frozen or finetuned predictive-pretrained encoder improves exact PTP on Square / ToolHang.

No experiment has run yet. No effectiveness conclusion exists.
