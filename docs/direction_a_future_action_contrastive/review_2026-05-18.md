# Direction A Review

Date: 2026-05-18

## Verdict

Direction A is worth validating, but it is not implementation-ready until a few details are fixed. The plan has the right control experiments: `B1`, `B2`, `O1`, and `O2` are enough for the first pass, and `O3` should stay second-pass.

The biggest risk is not the contrastive idea itself. The bigger risk is an ambiguous implementation that changes the policy condition shape, action alignment, or encoder capacity in a way that makes results hard to interpret.

## Strong Points

- Uses future expert actions as a behavior-level supervision signal, which is a reasonable proxy for latent belief under partial observability.
- Uses soft action similarity instead of hard positive/negative thresholds, which should be easier to stabilize.
- Includes `same architecture no-pretrain` baseline, which is necessary to separate objective benefit from extra parameters.
- Separates frozen and finetuned use, which can test whether diffusion loss damages or improves the pretrained representation.
- Delays hard negatives until the soft baseline is understood.

## Must Resolve Before Implementation

1. **Action-window alignment must be exact.**

   Current image transformer policy slices executed actions using `start = n_obs_steps - 1` and `end = start + n_action_steps`. For `n_obs_steps=2, n_action_steps=8`, that means the policy acts on normalized action indices `[1:9]` from the dataset window. Direction A should define `A_i+` with the same indexing, otherwise the contrastive target and downstream policy target can be off by one.

2. **Condition concat needs a concrete tensor design.**

   Current `TransformerForDiffusion` expects condition shape `B x To x Do`; `T_cond = 1 + n_obs_steps`. A naive extra-token concat changes the number of condition tokens and requires modifying `T_cond`, `cond_pos_emb`, and causal `memory_mask`.

   Lowest-risk first implementation: compute `z_t`, project it to `Dz`, repeat it across the `To` observation tokens, and concatenate on feature dimension:

   ```text
   cond = concat(nobs_features, repeat(z_t, To), dim=-1)
   ```

   Then instantiate the transformer with `cond_dim = Do + Dz`. This keeps condition token count unchanged.

3. **B2 must match O1/O2 architecture exactly.**

   `B2` should include the same history aggregator, projection, and fusion path as the contrastive model, but trained without contrastive pretraining. Otherwise `O1 > B2` is not interpretable.

4. **The contrastive loss should exclude the diagonal.**

   If `q_ii` and `p_ii` are included, the self-pair can dominate the row distribution and make the loss less informative. First implementation should mask diagonal entries before row softmax.

5. **Action normalization and action component weighting must be explicit.**

   Use the same normalized action tensor as the downstream DP/PTP training target. For robomimic absolute action, rotation representation and gripper dimensions can still dominate or under-contribute after naive flattening. Start with normalized L2, but log per-component distance contributions.

6. **`sigma` should not be a blind fixed value.**

   A robust first pass is to set `sigma` from the batch action-distance distribution, for example median non-diagonal distance or an EMA of it. Fixed `sigma` can make `q` nearly one-hot or nearly uniform depending on task.

7. **Define frozen/finetune precisely.**

   The plan should say whether frozen means:

   - freeze only visual backbone,
   - freeze visual backbone + temporal aggregator,
   - freeze the whole contrastive history encoder including projection-to-condition,
   - or freeze only the contrastive projection head.

   For policy experiments, the contrastive projection head used only for pretraining should usually be discarded; the representation projection used for condition fusion should be the controlled part.

8. **Need offline representation checks before policy training.**

   Before spending GPU on full policy runs, log:

   - contrastive train/val loss,
   - embedding variance or covariance spectrum,
   - nearest-neighbor future-action distance,
   - retrieval quality by future-action similarity,
   - whether embeddings collapse.

9. **Hard negatives should be delayed.**

   Hard negative mining based on visual similarity can add substantial compute and confounds. First validate soft contrastive. Add hard negatives only after `O1` is close to or better than `B2`.

10. **History action input needs a fair baseline.**

   If Direction A uses historical actions in the encoder input, `B2` must also use historical actions through the same architecture. Otherwise gains may come from adding action history rather than future-action contrastive pretraining.

## Recommended First-Pass Experiment Design

### Pretraining Smoke

- Task: Square first, then ToolHang.
- Input: start with `o_{t-H:t}` only if using current dataset path is simpler; add `a_{t-H:t-1}` only when B2 can match it.
- Target: normalized downstream action chunk aligned with policy slicing.
- Loss: diagonal-masked soft CE between action-similarity distribution and embedding-similarity distribution.
- Metrics: loss, embedding variance, nearest-neighbor action distance, action-similarity retrieval.

### Policy Validation

Minimum matrix:

```text
B1. Existing PTP baseline
B2. PTP + same history encoder/fusion, no contrastive pretraining
O1. PTP + contrastive history encoder, frozen
O2. PTP + contrastive history encoder, finetuned
```

Run Square before ToolHang for implementation smoke, but do not judge method effectiveness on Square alone.

## Open Questions For Discussion

1. What history length `H` should Direction A use in first pass: current `n_obs_steps=2`, PTP long-history setting, or a separate history encoder window?
2. Should `z_t` be a single global token repeated across condition tokens, or should the temporal encoder output a sequence aligned to obs tokens?
3. Should historical action input be included in the very first implementation, or deferred to avoid widening the first baseline matrix?
4. What exact PTP baseline score/checkpoint is the reference for Square and ToolHang?
5. Should first policy validation use cached embeddings to isolate policy training from encoder compute, or train encoder online end-to-end for `O2`?

## Recommendation

Proceed with Direction A after resolving the tensor fusion and indexing details. I would not request GPUs for full policy training until a small CPU/GPU smoke validates:

```text
dataset sample -> history encoder -> contrastive loss -> saved encoder checkpoint -> policy config loads the encoder -> one batch forward/backward
```

No experiment result exists yet, so this direction remains unvalidated.
